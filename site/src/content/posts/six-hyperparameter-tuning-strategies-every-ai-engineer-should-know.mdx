A tuning budget is easy to spend and hard to justify. The usual failure is not picking the wrong algorithm; it is spending GPU time or API calls on comparisons that teach you almost nothing, then letting the test set quietly influence the search. Choose tuning strategies by information gained per unit of budget, not sophistication. That means defining comparable trials, spending resources deliberately, and freezing selection before final evaluation.

The practical default is boring for a reason: use manual search to debug a few knobs, random search when you do not know which dimensions matter, Bayesian optimization when each trial is expensive, and successive halving or Hyperband when partial progress predicts final quality. Keep validation for selection and the test set for final reporting. If you get those two rules wrong, the search method barely matters.

## Define the objective before you spend compute

If the objective is fuzzy, every tuner looks worse than it is. Before the first trial, write down the metric and its direction, the constraints, the search space, the resource unit, the seed policy, and the split policy.

For a real tuning job, that usually means:

- **Metric:** validation loss lower is better, exact match higher is better.
- **Constraints:** maximum memory, latency, token budget, or spend; minimum quality.
- **Search space:** learning rate, batch size, LoRA rank, context length, prompt variant, retrieval top-k, decoding parameters.
- **Resource unit:** epochs, optimizer steps, examples, tokens, GPU-minutes, or paid API calls.
- **Seed policy:** shared seeds for selection; fresh, predefined seeds for finalist confirmation.
- **Split policy:** training, validation, and test, with test access withheld until selection is frozen.

The resource unit matters more than most teams admit. Equal epochs do not mean equal update counts, and equal optimizer steps do not mean equal data exposure when batch size changes. Log the comparison resource alongside tokens, examples, updates, and actual spend.

### Choose ranges that match the parameter type

Use log-scaled ranges for learning rate and weight decay when searching across orders of magnitude. Batch size and LoRA rank are discrete and hardware-bound. Context length, retrieval depth, and decoding settings should respect latency and token budgets.

For LLM systems, longer contexts also change inference memory and computation through attention and the KV cache. Prompt variants, retrieval settings, and fine-tuning recipes compete for budget differently. Without an explicit resource unit, the search can end up optimizing whichever knob is cheapest to evaluate.

## Manual search diagnoses interactions; it does not prove optimality

Manual search earns its keep when the space is small and the system is not understood well enough to automate. It is a fast way to debug a recipe, especially when you need to see how a change behaves before and after another change.

Change one factor, log the result, then check whether the delta survives when you vary a second factor. This works well for prompt variants, retrieval cutoffs, decoding temperature, or a small fine-tuning recipe.

The weakness is structural. One-factor-at-a-time search misses interactions like learning rate times batch size, retrieval top-k times context length, or LoRA rank times learning rate. It also invites adaptive overfitting: repeated inspection of validation feedback teaches you the split’s quirks, even when no validation label enters training.

## Grid search buys coverage at multiplicative cost

Grid search is legible and reproducible. scikit-learn’s `GridSearchCV` exhaustively evaluates a specified parameter grid with cross-validation [documentation](https://scikit-learn.org/stable/modules/grid_search.html). That clarity is also the trap.

**ESTIMATE, assuming three folds and 20 GPU-minutes per fit.** Six knobs with five values each produce `5^6 = 15,625` configurations. Without reuse, the cost is `15,625 × 3 × 20 / 60 = 15,625` GPU-hours. Sixty random configurations cost `60 × 3 × 20 / 60 = 60` GPU-hours under the same assumptions.

Grid search is worth it when the space is tiny, discrete, and low-dimensional. Once the space grows, it spends trials on arbitrary discretization and overcommits to dimensions that may not matter.

| Strategy | Exploration / reuse | Compute behavior | Native early stopping | Choose when |
|---|---|---|---|---|
| Manual | Expert-directed; informal reuse | Few trials, substantial human attention | No | Debugging a few understood knobs; then check interactions |
| Grid | Exhaustive specified combinations; no reuse | Multiplicative explosion | No | Tiny discrete spaces; interaction coverage matters |
| Random | Independent samples; no reuse | Explicit trial budget; parallel-friendly | No | Important dimensions are unknown |
| Bayesian | Adaptive, model-guided proposals | Sample efficiency; optimizer overhead and parallelism trade-offs | No; add pruning | Expensive, sufficiently stable objectives with exploitable structure |
| Successive halving | Proposal method separate from allocation | Many short trials, progressively fewer survivors | Yes | Meaningful resource axis and predictive early rankings |
| Hyperband | Multiple halving brackets | Spreads budget across starting resources and populations | Yes | Unsure how much resource to allocate initially |

“Native” excludes independently attached pruning callbacks. None guarantees better final quality.

## Random search explores more distinct values of important dimensions

Random search is the default when you do not know which parameters matter most. Bergstra and Bengio explain why it often beats grid search in high-dimensional spaces: when only a few dimensions strongly affect performance, random search explores more distinct values along those dimensions [paper](https://jmlr.org/papers/v13/bergstra12a.html).

A grid repeatedly evaluates the same coordinate values across combinations of other parameters. Random search samples from the declared distributions, giving continuous dimensions more distinct values within a fixed trial budget. It does not adapt to observed uncertainty or learn which dimensions matter.

Use distributions, not just fixed lists. Log-uniform sampling is a useful default for learning rate and regularization across orders of magnitude. Use hardware-compatible discrete choices for batch size, and feasible ranges for retrieval depth, context length, and decoding settings.

## Bayesian optimization pays when evaluations dominate overhead

Bayesian optimization earns its complexity when each evaluation is expensive. Fit a surrogate model to observed trials, then use an acquisition function to balance predicted quality and uncertainty when choosing the next trial.

Expected improvement considers the expected magnitude of improvement over an incumbent. Probability of improvement considers the chance of beating it, not the size of the gain. Upper confidence bound combines a predicted value with an uncertainty bonus; the corresponding minimization convention reverses the direction.

Gaussian-process methods use probabilistic regression. Tree-structured Parzen estimators, such as Optuna’s TPE approach, model parameter distributions associated with better and worse observations and support mixed parameter types [Optuna documentation](https://optuna.readthedocs.io/en/stable/).

The trade-offs are real:

- Noise can obscure the response surface.
- Constraints and conditional branches can create discontinuities.
- Mutable evaluation dependencies make historical observations incomparable.
- Parallel proposals have incomplete information about pending trials.

For paid evaluation, budget every call—not just candidate generation. **ESTIMATE, assuming an all-in price of $0.01 per call:** 60 configurations × 500 examples × 3 repeats × 2 calls per example—one candidate and one judge—equals 180,000 calls. Assuming retries add 10%, the total is `180,000 × 1.10 × $0.01 = $1,980`. Different candidate and judge prices require separate terms; token-dependent billing requires token counts instead.

## Successive halving needs early rankings you can trust

Successive halving separates candidate proposals from resource allocation. The proposal method can be random, Bayesian, or manual. Pruned trials supply partial or censored evidence, not completed final-budget scores; the sampler/pruner integration must handle that distinction. Do not pass early losses to an arbitrary optimizer as if every configuration completed the same budget.

Start many configurations with a small budget, keep the best fraction, increase survivors’ budgets, and repeat. scikit-learn’s halving search classes are experimental and require enabling the experimental import before importing them [HalvingGridSearchCV documentation](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.HalvingGridSearchCV.html).

With checkpoint continuation, consider 27 configurations at one epoch, nine promoted to three epochs, three to nine, and one to 27. Incremental work is `27 + 9×2 + 3×6 + 1×18 = 81` configuration-epochs, versus `27×27 = 729` for full evaluation of every configuration. This excludes overhead and does not imply equivalent final quality. Restarting survivors instead of continuing checkpoints changes the arithmetic.

Warmup, regularization, larger models, and crossing learning curves can make strong final configurations look weak early. Complete several calibration trials and compare early-versus-final rankings before enabling aggressive pruning. If early rankings are unreliable, increase the minimum resource or disable pruning.

## Hyperband hedges the starting-resource choice

Hyperband extends successive halving with multiple brackets using different starting budgets and population sizes [paper](https://www.jmlr.org/papers/v18/16-558.html). It spreads resources across broad, aggressive exploration and narrower searches with more initial training.

Ray Tune provides HyperBand and ASHA, an asynchronous successive-halving scheduler [documentation](https://docs.ray.io/en/latest/tune/index.html). Hyperband’s defining distinction is its multiple resource brackets. ASHA’s defining distinction is asynchronous promotion and stopping decisions, avoiding the need to wait for all trials at a rung. Asynchrony addresses scheduling efficiency; it does not repair misleading early metrics.

## Validation selects; the test set reports

Use validation for every selection decision: model, prompt, retrieval settings, decoding parameters, pruning thresholds, and stopping criteria. Freeze the complete recipe before evaluating test data.

Use shared validation examples and a predefined selection seed or matched seed schedule across configurations. For two scores, the variance of their difference equals the sum of their variances minus twice their covariance. Shared randomness can therefore reduce comparison variance when outcomes are positively correlated. It is not a guarantee, and the seed must never become a tuned parameter.

Confirm a small, predefined finalist set across fresh, predefined seeds using validation only. Then freeze the winner. New seeds probe stochastic sensitivity; they do not remove adaptive overfitting to the validation examples.

For small or noisy datasets, use nested cross-validation or fresh confirmation data. Splits must respect the deployment structure: keep related users, documents, or entities together, and use chronological boundaries when predicting future observations. In nested CV, tune only within each outer training partition using inner splits; evaluate the selected procedure on the outer fold without feeding outer-fold results back into selection [nested-CV example](https://scikit-learn.org/stable/auto_examples/model_selection/plot_nested_cross_validation_iris.html). Fresh confirmation data reduces future adaptive overfitting but does not erase prior leakage.

### Persist selection before opening the test holdout

This synthetic IID example uses training-only scaling, shared selection randomness, validation-based pruning, and three-finalist confirmation before persisting the winner. SQLite stores trials and metadata; mismatched data, script, dependencies, or objective settings block resumption. It does not enforce test permissions or implement a distributed budget service.

Install the dependencies without package pins:

```bash
pip install numpy scikit-learn optuna
```

The example requires Python 3.10 or newer syntax and uses Optuna’s `TPESampler`, `MedianPruner`, trial reporting, and RDB storage APIs.

```python
import hashlib
import platform
import time
from importlib.metadata import version
from pathlib import Path

import numpy as np
import optuna
from sklearn.datasets import make_classification
from sklearn.linear_model import SGDClassifier
from sklearn.metrics import log_loss
from sklearn.model_selection import train_test_split
from sklearn.preprocessing import StandardScaler

SELECTION, CONFIRM, REPORT = 1000, [101, 202, 303], [404, 505, 606]
EPOCHS, CHUNK, LIMIT = 12, 64, 30
X, y = make_classification(n_samples=6000, n_features=20,
                          n_informative=8, n_redundant=2, random_state=7)
a, b = train_test_split(np.arange(len(y)), test_size=0.3,
                       stratify=y, random_state=7)
v, t = train_test_split(b, test_size=0.5, stratify=y[b], random_state=7)
scaler = StandardScaler().fit(X[a])
train, val, test = [(scaler.transform(X[i]), y[i]) for i in (a, v, t)]

def score(model: SGDClassifier, data: tuple) -> float:
    return float(log_loss(data[1], model.predict_proba(data[0]), labels=[0, 1]))

def fit(params: dict, seed: int, trial: optuna.Trial | None = None):
    model = SGDClassifier(loss="log_loss", learning_rate="constant",
                          eta0=params["learning_rate"], alpha=params["alpha"],
                          random_state=seed)
    rng = np.random.default_rng(seed)
    for epoch in range(EPOCHS):
        order = rng.permutation(len(train[1]))
        for start in range(0, len(order), CHUNK):
            idx = order[start:start + CHUNK]
            model.partial_fit(train[0][idx], train[1][idx], classes=[0, 1])
        if trial is not None:
            trial.report(score(model, val), step=epoch)
            if trial.should_prune():
                raise optuna.TrialPruned()
    return model

def objective(trial: optuna.Trial) -> float:
    params = {"learning_rate": trial.suggest_float("learning_rate", 1e-5, 1e-1, log=True),
              "alpha": trial.suggest_float("alpha", 1e-6, 1e-2, log=True)}
    trial.set_user_attr("seed", SELECTION)
    started = time.monotonic()
    try:
        return score(fit(params, SELECTION, trial), val)
    finally:
        trial.set_user_attr("runtime_seconds", time.monotonic() - started)

identity = {
    "objective": "validation-log-loss-v1",
    "script_sha256": hashlib.sha256(Path(__file__).read_bytes()).hexdigest(),
    "data_sha256": hashlib.sha256(X.tobytes() + y.tobytes()).hexdigest(),
    "python": platform.python_version(),
    "packages": {p: version(p) for p in ("numpy", "scikit-learn", "optuna")},
    "seeds": [7, SELECTION, CONFIRM, REPORT], "epochs": EPOCHS, "chunk": CHUNK,
    "trial_limit": LIMIT, "timeout_seconds": 600,
    "sampler": ["TPE", 17], "pruner": ["Median", 5, 3, 1],
}
study = optuna.create_study(
    direction="minimize", study_name="sgd-validation-v1",
    storage="sqlite:///tuning.db", load_if_exists=True,
    sampler=optuna.samplers.TPESampler(seed=17),
    pruner=optuna.pruners.MedianPruner(
        n_startup_trials=5, n_warmup_steps=3, interval_steps=1))
old = study.user_attrs.get("identity")
if (old is None and study.trials) or (old is not None and old != identity):
    raise RuntimeError("Study identity mismatch; use a new study.")
study.set_user_attr("identity", identity)
if "winner" not in study.user_attrs:
    study.optimize(objective, n_trials=max(0, LIMIT - len(study.trials)), timeout=600)
    completed = [r for r in study.trials if r.state == optuna.trial.TrialState.COMPLETE]
    finalists = sorted(completed, key=lambda r: (r.value, r.number))[:3]
    if len(finalists) != 3:
        raise RuntimeError("Three completed finalists are required.")
    started = time.monotonic()
    confirmation = [{"trial": r.number, "params": r.params,
                     "losses": [score(fit(r.params, s), val) for s in CONFIRM]}
                    for r in finalists]
    winner = min(confirmation, key=lambda r: (np.mean(r["losses"]), r["trial"]))
    study.set_user_attr("confirmation", confirmation)
    study.set_user_attr("confirmation_seconds", time.monotonic() - started)
    study.set_user_attr("winner", winner["params"])
if "test_report" not in study.user_attrs:
    losses = [score(fit(study.user_attrs["winner"], s), test) for s in REPORT]
    study.set_user_attr("test_report", {"seeds": REPORT, "losses": losses})
losses = study.user_attrs["test_report"]["losses"]
print(f"Frozen test loss: {np.mean(losses):.4f} ± {np.std(losses, ddof=1):.4f}")
```

The fixed `partial_fit` chunk size controls processing partitions, not neural-network minibatch gradient averaging. Real neural-network batch size remains a legitimate search dimension, with resource-comparability and memory consequences.

Optuna’s `timeout` does not interrupt an in-flight trial. This script caps additional trials against the stored count, but a resumed invocation receives another admission-time window. A seeded sampler also does not persist its evolving random-generator state here, so resumption preserves objective identity—not an identical uninterrupted proposal sequence. Use one process for this example; concurrent initialization and report writes require stronger coordination.

For real protection, put test data behind separate permissions or an evaluator service. Persisting a winner is a useful boundary, not an access-control mechanism.

### Report variability without overstating certainty

Seed standard deviation measures stochastic variability on a fixed dataset. Fold standard deviation includes variation from data splits and is not automatically a standard error, especially with overlapping training partitions. Neither alone is a confidence interval for deployment performance.

Report the seed schedule, split construction, number of runs, and what the dispersion measures. Do not select the best seed or combine seed and fold variability into an unexplained “±” number.

## Production tuning fails through budgets, invalid spaces, and drift

| Symptom | Cause | Mitigation |
|---|---|---|
| Strong final configurations disappear early | Warmup or crossing learning curves | Complete calibration trials; increase minimum resource or disable pruning |
| Trials crash instead of losing fairly | Invalid conditional combinations, OOM, or infrastructure failure | Encode valid branches; record OOM and infrastructure failures separately; do not convert every exception into a bad score |
| Offline validation improves while deployment degrades | Adaptive overfitting or unrepresentative splits | Use grouped/time-aware splits and fresh confirmation data; require representative deployment validation after offline selection |
| Budget is exceeded under load | Workers dispatch against stale remaining-budget counters | Reserve budget atomically; cap outstanding jobs; reconcile actual charges |
| The winner changes week to week | Mutable model, corpus, judge, or caching dependencies | Snapshot the evaluation dependency graph; retain baseline canaries; separate drift from tuning |

A timeout is not a spend ledger. Likewise, recording a configuration is not enough if the model alias, judge, corpus snapshot, or caching policy changes underneath it.

## What most teams get wrong

- **Uniform ranges across orders of magnitude:** use log distributions for learning rate and regularization.
- **Selecting only on quality:** impose latency, memory, and token-cost constraints during selection.
- **Reporting the best seed:** use predefined matched schedules and report their dispersion.
- **Treating coordinate search as interaction coverage:** use it for diagnosis, then test coupled knobs jointly.
- **Refreshing the test set after leakage:** new data supports future evaluation; it does not rehabilitate contaminated results.

## Choose by cost, dimensionality, and early signal

1. **Define comparable trials.** Fix the metric, constraints, resource unit, splits, and seed schedules.
2. **Choose the proposal method.** Manual or grid for tiny spaces; random for unknown important dimensions; Bayesian optimization for expensive, sufficiently stable objectives.
3. **Choose resource allocation separately.** Add halving when early rankings predict final quality; use Hyperband to spread risk across starting-resource choices.
4. **Make the study resumable.** Persist configuration, runtime, data and objective identities, and failure categories.
5. **Confirm and freeze.** Compare a small finalist set on validation across fresh predefined seeds, then freeze the recipe before test evaluation.
6. **Validate deployment relevance.** Report clearly defined variability and require representative deployment validation without turning the final holdout into tuning feedback.

The right strategy is the one that buys useful comparisons within your budget. Sophistication does not compensate for incomparable trials, misleading early rankings, or a test set that became feedback.
